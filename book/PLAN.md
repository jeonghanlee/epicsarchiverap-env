# Book plan

This plan fixes the structure of the book in `book/src`. It is not rendered. Every page is written from the code, the configuration and commands run on a host; the earlier README files of `docs/` are not a source.

## Tool versions

The workflow `.github/workflows/book.yml` builds the book with mdBook 0.5.4 and checks the SHA-256 of the downloaded archive. Build locally with the same version so that a page renders as it is published. The job `generated` runs `make init` and `book/scripts/check-generated.bash`, so a generated page that differs from its generator is reported on every push and pull request that changes the code it reads.

## Rules of the book

- One page has one type: concept, procedure, reference or tutorial. The title form follows the type: a noun phrase for concept and reference, an imperative for procedure and tutorial.
- A procedure page has an introduction, Prerequisites when there are any, numbered one-action steps and a Verification section.
- A command is published only after it ran as shown on a host. A page whose commands cannot run on the available host does not show them; it says so in its introduction.
- Reference tables that restate code (variables, make targets, script options, judgement thresholds) are generated from the code by a script under `book/scripts/`, so the page and the code cannot differ.
- Headings use sentence case and 3 to 11 words. `SUMMARY.md` reaches every page.

## Structure

Verification classes: **H** the commands run on this host as shown; **S** they run against a scratch appliance started from the built WARs; **P** only a plan or a read-only output can run here (the real step needs root, systemd or a VM), so the page shows only what ran.

## Tutorial decision

The book has no tutorial. A tutorial would repeat "Install an appliance with SQLite" and "Archive a test PV and check the stored samples" step for step, and the install step needs root and systemd, so no host here can show each result. This is the reason recorded for skipping, to be restated in the introduction when the first procedure page lands.

## Order of writing

1. Concept pages of Part 1 and the reference pages generated from code (Part 4, Part 6 judgements, appendices): they need only a read of the code and run on this host.
2. Procedures that run on a scratch appliance (Parts 5 and 6).
3. Build and test procedures (Parts 3 and 7).
4. Install procedures that only a plan can show (Part 2), with the limit stated.
5. Glossary and the introduction's final form.
6. GitHub Actions deployment, last.

## Open decisions for the owner

- Pages of class P show only `--plan` output or read-only output; say whether a disposable VM may be used later to run the install steps for real.
- The interface is part of the source repository; the book describes it as the selected source carries it, and the judgements page is generated from that source's `judge.js` (`AA_SOURCE_CLONE` overrides the clone).

## Status

All 32 pages are written from the code and from commands run on the author's host. The classes of the plan hold as follows.

| Class | Pages | What ran |
| :--- | :--- | :--- |
| H | Part 1, Part 3, Part 4, the local suite, the appendices | The commands ran as shown on the author's host |
| S | Operate pages, Work page procedure | Not run against an appliance: the host serves a live archive. The pages state this and quote the script source |
| P | Part 2 install pages, VM tests | `--plan` and read-only commands ran; the pages state that the install step was not run |

The generated pages are regenerated with `bash book/scripts/generate-all.bash` and checked with `bash book/scripts/check-generated.bash`.

## Observations about the code

Found while writing, outside the book:

- `scripts/archappl.bash` listed `h` as "this screen" in its usage while the `h` case did nothing; the argument is removed from the usage and is now an unknown argument, and `help` prints the usage.
- The help text of the Makefile took the second line of a two-line comment as the description of `copy.ui`; the comment was rewritten so the description is one line.
- The `<os>.conf` targets delete `configure/CONFIG_SITE.local` and rewrite it, and the installers run them first; site values belong in `../CONFIG_SITE.local`.
