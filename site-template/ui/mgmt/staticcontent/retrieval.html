Retrieval performance

For a person whose data requests are slow or fail, and for the person helping them. It shows what the server can say about reading and measures what this browser sees.

Measure from this browser

Question
How long does a data request take for me, now?
Slow is
More than about a second for the last hour of one PV, or a time that grows with the length of the range.
Then
Compare with the server side below. A slow request while the retrieval heap floor is high or the ETL is running points to the server; a slow request with a quiet server points to the network or to the size of the request.

WhenPVRangeSamplesSizeFirst byteComplete

The measurement is one ordinary data request made by this page; nothing on the server changes. The results of this visit are kept on the page only.

The whole answer is read into this page, at about 100 bytes per sample. For a PV that changes once a second, a day is about 9 MB, a week about 60 MB and 30 days about 250 MB; a faster PV needs proportionally more. Start with the last hour or the last day.

What the server says

A problem is
A retrieval process that is down.
Attention when
The heap floor climbs from day to day; the note under the heap chart says so.
Not a problem
An ETL pass that is running now. It is normal work and can make a request slower while it runs.

The server counts requests and users but does not record how long a request took. That is why the measurement above is made in the browser.

Where data lives

Data moves from the short term store through the medium term store to the long term store as it ages, at the cadence of the ETL. Recent data is read from the short term store; a long range reads files of several stores, and a policy may keep only reduced values in the long term store. This is why old data and long ranges are slower than recent data. The policy of a PV is shown in its stores above.
