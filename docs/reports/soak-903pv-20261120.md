# Archiver Appliance 903-PV day run on the version commit 105b1b10 of release Ahsoka

Report date: 2026-11-22

## Scope

This report records the statistics and the method of one 24-hour run in which an appliance built and installed from the source commit `105b1b10795f1826318d6c0834ab55a8e09225b7` of the repository `epicsarchiverap-maven` archives 903 process variables (PVs) on a fresh guest. The run repeats the day run of the source tag `2026-10` (`docs/reports/soak-903pv-20261026.md`, commit `587df6e`) with the same PV set, the same checks C1 to C9 and, apart from the changes listed in the section Differences from the run of 2026-10, the same scripts. It is the run of Release Verification 15 of release Ahsoka in the register of the repository `epicsarchiverap-maven`.

The extract, transform and load component (ETL) moves data from one store to the next. A JVM is a Java virtual machine, and JDK 21 is the Java Development Kit in version 21. An IOC is an input/output controller, here a soft IOC that serves the PVs. The hold of a store is an age. With the setting `gather=1` of the short-term store (STS) and the medium-term store (MTS), a partition file is eligible to move to the next store when hold + 1 partition lengths have passed since the start of its partition, and the next ETL pass moves it. The checks C1 to C9 have the definitions of the record of 2026-10 (Result per check and Method); the section Method below lists what this run read.

Sizes of responses and memory are given in MiB (1,048,576 bytes) and disk space in GiB, as the tools report them. The rates that the appliance reports in GB per day keep the unit of the appliance.

**Out of scope:** the transfer from the MTS to the long-term store (LTS) and the reduction of the long-term store, a restart of the appliance under load, heap sizing, and the verdict on the release. The verdict belongs to the owner of the repository `epicsarchiverap-maven` and is entered in its work register.

## Method

The checks C1 to C9 are read as in the record of 2026-10; this section lists what was run.

### Preparation, registration and load

1. The guest is created fresh. The EPICS tree, `ioc-runner` and `procServ`, the package `libevent-pthreads-2.1-7t64` (needed by `softIocPVX`) and the scripts are copied or installed on the guest before the installer runs.
2. The installer of this repository (`install-local-sqlite.bash -y`) builds and installs the appliance at the source pin above.
3. The soft IOC is installed and started with `ioc-runner --local` from the folder `iocBoot/iocAasoak` (the three definition files; loopback network settings; `EPICS_CA_MAX_ARRAY_BYTES` 16384). All 903 names are read with Channel Access on the loopback address.
4. All 903 PVs are registered in one `archivePV` request by `register.py` with the rows of `pvs-all.csv` (sampling period, method and policy of each row). `poll_status.py` waits until all report `Being archived`.
5. The collector `collect.py` runs every 600 s as a user timer and service from 30 minutes after the registration until 24 hours after the registration.

### Per cycle

The collector reads only. C1 reads `systemctl is-active` of the appliance unit and of the IOC unit and the number of `java` processes of the service account. C2 reads `getPVStatus` for the 903 names. C3 and the event rate read `getApplianceMetrics`. C4 retrieves the closed window of 600 s that ends 120 s before the cycle for the six sample PVs and compares the returned count with the expected count; the result applies 99 percent to every recorded ratio. C5 reads the three lists of dropped events with limit 1000. C6 reads `getSilentPVsReport` with limit 2000 and counts a PV as stale when its last event is older than 60 s, for the 823 PVs whose names start with `AASOAK:L1:`, `AASOAK:L2:`, `AASOAK:L2F:`, `AASOAK:L2WF:`, `AASOAK:FAST:` and `AASOAK:SLOW:`. C7 reads `ps` for the resident set and `df` for the filesystem of the stores. The five added columns read `/proc/loadavg` and `/proc/PID/stat`.

### After the window

`final-measure.py` runs as root after the window: the whole-day retrievals of the sixteen PVs, the resident set of the retrieval JVM before and after, the retrieval of the last closed hour for all 903 PVs, the version strings, the store folders of the six sample PVs and the storage metrics. The ETL counters are read from `getInstanceMetrics`. The runs of the scheduled health service are counted in the system journal of the guest for the period, with the bounds given in UTC. `summarize.py` condenses the 141 cycles of `evidence/soak-log.csv` into the statistics above.

## Limits of the run

- The MTS-to-LTS transfer and the reduction of the long-term store are not covered, because a daily MTS file is eligible to move to the LTS only three days after the start of its partition.
- A restart of the appliance under load is not part of this run.
- The retrieval memory protection refuses or cuts none of the sixteen retrievals, so the run does not show how the protection acts; it shows that retrievals of up to 654 MiB return completely. The resident set of the retrieval JVM is read once before the first and once after the last retrieval (435 and 436 MiB); the peak during the retrievals is not sampled.
- The collector has no cycle before 2026-11-21T00:23:24Z and none after 2026-11-21T23:43:24Z, 10 minutes before the end of the 24 hours after the registration. The appliance, the IOC and the four JVMs were active at the measurements after the window.
- Check C4 covers six PVs in each cycle; the 893 PVs are checked once, for one closed hour at the end. Check C4 cannot apply the period rule to the `deadband` group, because the group is change-driven.
- Check C6 covers 823 of the 903 PVs.
- Checks C3 and C5 are sampled every 600 s; a loss and recovery inside one interval is not visible.
