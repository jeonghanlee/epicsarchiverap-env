# Archiver Appliance 903-PV day run on the source tag 2026-10

Report date: 2026-10-27

## Scope

This report records the statistics and the method of one 24-hour run in which an appliance built and installed from the source tag `2026-10` archives 903 process variables (PVs). The statistics are condensed from the measurements of the run. The raw measurement files and the small measurement scripts are not retained; the Method section defines what the collector and the measurements after the window read and compute.

The extract, transform and load component (ETL) moves data from one store to the next. A JVM is a Java virtual machine, and JDK 21 is the Java Development Kit in version 21. An IOC is an input/output controller, here a soft IOC that serves the PVs. The hold of a store is an age. With the setting `gather=1` of the STS and the MTS, a partition file is eligible to move to the next store when hold + 1 partition lengths have passed since the start of its partition, and the next ETL pass moves it. The checks C1 to C9 are defined in the section Result per check and in Method.

Sizes of responses and memory are given in MiB (1,048,576 bytes) and disk space in GiB, as the tools report them. The rates that the appliance reports in GB per day keep the unit of the appliance.

**Out of scope:** the transfer from the medium-term store (MTS) to the long-term store (LTS) and the reduction of the long-term store, a restart of the appliance under load, heap sizing, and the verdict on the release. The verdict belongs to the owner and is entered in the work register.

## Load

The load is 903 PVs served by one soft IOC (`softIocPVX`, a `st.cmd` that loads the three definition files, run as a user service). The Channel Access and PV Access servers listen on the loopback address only, and `EPICS_CA_MAX_ARRAY_BYTES` is 16384. The PV definitions are the files `fixtures/aasoak.db` (100 archived PVs), `fixtures/load1.db` (400) and `fixtures/load2.db` (403) of `tests/archiver-soak` in the repository `ansible-provision`, with the table `fixtures/pvs-all.csv`. ## Method

### Registration and load

1. Install the appliance from the source tag with the SQLite installer and start the soft IOC with the three definition files above.
2. Register all 903 PVs in one `archivePV` request to the management interface. Each entry carries the sampling period and method of its row in `pvs-all.csv`. When the row has a policy, the entry carries it too: `VeryFast` for the 110 PVs of 0.1 s, `Fast` for the 10 `deadband` PVs, `Medium` for the 10 `slow` PVs; the other 773 PVs carry no policy. Wait until all report `Being archived`.
3. Run the collector below every 600 s until about 24 hours after the registration. The run has 142 cycles from 2026-10-26T17:32:40Z to 2026-10-27T17:02:41Z, which is 23.5 hours.

### Per cycle

The collector reads only.

| Check | Source |
| :--- | :--- |
| C1 | `systemctl is-active` of the appliance unit and of the IOC unit; the number of `java` processes of the service account |
| C2 | `getPVStatus` of the management interface for the 903 names; the count of `Being archived` |
| C3 | `getApplianceMetrics`: connected and disconnected PV counts |
| C4 | retrieval (`getData.json`) of the closed window of 600 s that ends 120 s before the cycle, for the six sample PVs; the collector records the returned and the expected count (600 divided by the sampling period) of each; the result applies 99 percent to every recorded ratio (the collector's own pass column uses 98 percent, and the lowest recorded ratio is 1.0002) |
| C5 | `getPVsByDroppedEventsBuffer`, `getPVsByDroppedEventsTimestamp`, `getPVsByDroppedEventsTypeChange` with limit 1000; the length of each list |
| C6 | `getSilentPVsReport` with limit 2000; a PV is stale when its last event is older than 60 s; the check covers the PVs whose name starts with `AASOAK:L1:` (group `load1`, 400 PVs), `AASOAK:L2:` (`load2`, 300), `AASOAK:L2F:` (`load2fast`, 100), `AASOAK:L2WF:` (`load2wave`, 3), `AASOAK:FAST:` (`fast`, 10) and `AASOAK:SLOW:` (`slow`, 10), 823 PVs in all |
| C7 | `ps` resident set of the processes of the service account and of the IOC; `df` of the filesystem of the stores (rounded to whole GiB); `getApplianceMetrics` event rate and data rate |
| C8 | after the window, see below: the check passes when each of the sixteen whole-day retrievals returns HTTP 200, a complete response and at least 99 percent of the expected count, and when the listing of the folders shows the earlier data of the run in the MTS and only the latest hours in the STS |

### After the window

1. Whole-day retrievals of the sixteen PVs named above for the window above, each streamed and counted without storing the body. The HTTP status, the completeness of the response, the event count, the size and the duration are recorded. The resident set of the retrieval JVM is read before the first and after the last retrieval.
2. For all 903 PVs, a retrieval of the last closed hour. Expected count is 3,600 divided by the sampling period; the `deadband` group is reported without a period rule.
3. The version strings of the four components from `getVersions` and the appliance identity from `getApplianceInfo`.
4. The listing of the STS, MTS and LTS folders of the six sample PVs (file names and sizes), made as root because the store folders belong to the service account, and the ETL counters of `getInstanceMetrics`.
5. The runs of the scheduled health service: the number of `Finished` lines of the unit in the system journal for the period, and the number of lines that contain `FAIL`, `ERROR`, `SKIP`, `STARTING` or `Failed`.

## Limits of the run

- The MTS-to-LTS transfer and the reduction of the long-term store are not covered, because a daily MTS file is eligible to move to the LTS only three days after the start of its partition.
- A restart of the appliance under load is not part of this run.
- The retrieval memory protection refuses or cuts none of the sixteen retrievals, so the run does not show how the protection acts; it shows that retrievals of up to 653 MiB return completely. The resident set of the retrieval JVM is read once before the first and once after the last retrieval (507 and 508 MiB); the peak during the retrievals is not sampled.
- The collector has no cycle before 2026-10-26T17:32:40Z.
- Check C4 covers six PVs in each cycle; the 893 PVs are checked once, for one closed hour at the end. Check C4 cannot apply the period rule to the `deadband` group, because the group is change-driven.
- Check C6 covers 823 of the 903 PVs.
- Checks C3 and C5 are sampled every 600 s; a loss and recovery inside one interval is not visible.
- The store folders, the ETL counters and the version strings are read once, after the run.
- The scheduled health service verifies process presence and storage usage; it does not check application readiness.
- The pre-run PV `LocalInstall:6tZEpbpY:Value` is disconnected; the run does not exercise its connection.
