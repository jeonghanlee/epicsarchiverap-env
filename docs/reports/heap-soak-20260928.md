# Archiver Appliance heap observations from the Ansible soak

Report date: 2026-09-28

## Scope

This report summarizes the supplied Ansible soak measurements at 100, 500
and 903 process variables (PVs). It covers sampled Java heap usage,
resident set size (RSS), garbage collection (GC) counters, retrieval
response times and the limits of the available measurements.

**Out of scope:** a new test run, a production heap recommendation,
changes to JVM settings, GC tuning and storage capacity sizing.

The measurements support the heap investigation in
[the canonical work register](../milestone-265f580.md#m41---measure-per-component-heap-needs-by-archiving-load).
This report records evidence; it does not change that work item's status
or replace its completion criteria.

## Findings and their limits

The reported run used a 256 MiB heap for each of the four JVMs. No JVM
`OutOfMemoryError` was reported, and the only reported JVM PID changes
followed one planned appliance restart. A separate retrieval client was
killed by the kernel for an out-of-memory condition; the host as a whole
therefore did experience an OOM event.

ETL had the largest sampled heap usage in every load stage. Its highest
observed value was 250.9 MiB, approximately 98.0% of the configured
256 MiB maximum. This is a five-minute sample maximum. It does not
establish the instantaneous peak, the heap retained immediately after GC
or a safe operating margin.

The six-hour retrieval run reported 42,417 requests, all returning HTTP
200, with a median response time of 31 ms and a p99 of 98 ms. These
measurements describe that request workload; they do not establish
end-to-end latency for every archived PV.

The data are sufficient to compare the reported sampled usage across the
three stages. They are insufficient to derive a heap recommendation per
load: heap usage immediately after GC and individual GC pause durations
were not collected. The supplied response also states that the ongoing
new test collects the same GC fields, so these gaps remain in that test.

## Evidence basis

The numeric tables reproduce the Ansible response supplied on 2026-09-28.
That response states that its figures were recalculated from the original
CSV files. The original CSV files and sampler were not available in this
report's working checkout. Their calculations have not been independently
reproduced here. The report checks arithmetic within the supplied figures
and verifies the meaning of the cited `jstat` fields against the JDK 21
documentation.

The values apply to the source and environment revisions below. They do
not constitute a soak of the later aa-env configuration and runtime fixes.

## Sampled heap usage

Values are the maximum heap usage observed at five-minute sampling
intervals, in MiB. The retrieval column is a subset of the full 903 PV
stage, not a fourth independent load stage.

| Component | 100 PV | 500 PV | 903 PV, full stage | 903 PV with retrieval, six hours |
| --- | ---: | ---: | ---: | ---: |
| mgmt | 173.0 | 202.0 | 192.0 | 192.0 |
| engine | 187.4 | 195.4 | 227.3 | 227.3 |
| etl | 241.1 | 211.6 | 250.9 | 239.1 |
| retrieval | 188.5 | 184.8 | 197.7 | 179.2 |

The stage maxima are not monotonic in PV count. Observation durations
and retrieval conditions differ across stages.
These maxima alone do not establish a causal relationship between PV
count and required heap. Lower maxima in the retrieval subset do not
show that retrieval reduces memory usage.

The ETL value after a detected Full GC counter increase ranged from
49.5 to 211.6 MiB at the next regular observation. That observation could
be approximately five minutes after the collection. It cannot be used
as an immediate post-GC heap measurement.

## RSS and GC counters

This table covers the reported 404-observation interval from the start
of the 500 PV stage through the end of the run. It includes the final
fault tests. It is neither a table for the 903 PV stage alone nor a
per-stage GC comparison.

| Component | RSS range, MiB | Young GC increase | Full GC increase | GCT increase, s |
| --- | ---: | ---: | ---: | ---: |
| mgmt | 483.4-501.0 | 408 | 0 | 2.504 |
| engine | 412.8-452.2 | 7,417 | 0 | 57.832 |
| etl | 412.8-453.1 | 15,055 | 10 | 29.209 |
| retrieval | 399.5-424.2 | 11,967 | 0 | 15.491 |

One of the ten ETL Full GC events occurred in the 500 PV stage. The ten
events must not all be attributed to the 903 PV load.

Oracle defines `YGC` and `FGC` as event counts and `GCT` as total GC time
[1]. The reported GCT increases are cumulative time differences over
the observation interval. They do not provide individual pause durations,
maximum pause duration or pause p99. Young and Full GC times were not
retained separately in the supplied dataset, although `jstat` defines
separate `YGCT` and `FGCT` fields [1].

RSS is reported separately from Java heap usage. The four RSS maxima
must not be added and presented as a simultaneous observed total:
their timestamps are not supplied here.

The supplied response does not identify whether the initial client OOM
falls inside the final six-hour retrieval interval. The client failure
and the 42,417 HTTP 200 responses are therefore retained as separate
observations without assuming their temporal relationship.

## Measurements needed for heap sizing

| Measurement | Available evidence | Remaining gap |
| --- | --- | --- |
| Load definition | Three PV counts, periods, waveform counts and query workload | Original PV settings and exact stage timestamps are not attached |
| Sampled heap by component and load | Stage maxima at five-minute intervals | Immediate post-GC heap and instantaneous peaks are not measured |
| GC activity | Aggregate Young/Full GC count and GCT increases | Individual pauses and stage-specific counter deltas are not supplied |
| Process memory | Component RSS ranges over the combined interval | Per-stage distributions and concurrent total RSS are not supplied |
| Retrieval performance | Six-hour request count and response-time summary | Full-PV latency and returned-data completeness are not established by this summary |
| ETL performance | Store movement and cumulative metrics | Per-pass duration is not established by the 277 s value |

GC logs, Java Flight Recorder recordings and raw generation-level heap
values were not retained. The supplied measurements cannot reconstruct
the missing immediate post-GC values or individual pause distributions.
Collecting the same fields for longer would provide more periodic samples
but would not supply those missing measurements.

The supported conclusion is limited to observed operation and sampled
resource use under the documented test conditions. A per-load or
per-component heap recommendation, including its operating margin,
remains undetermined.
